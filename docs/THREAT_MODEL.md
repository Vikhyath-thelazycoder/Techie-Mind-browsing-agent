# Threat Model

**Status:** Phase 2 — Security + Privacy. Every threat of plan §44 with its asset, attacker, attack path, defense, residual risk and the test that proves the defense. Threats whose attack surface arrives in a later phase (models, monitoring, e-mail notifications) are listed with the defense already in place and what that phase must add.

Trust boundary: **untrusted** — web pages (text, DOM, redirects), model output (Phase 3), network responses, anything a page can make the extension observe. **Trusted** — the user's own request, the local action firewall, the privacy gate, extension storage (local, no sync).

| # | Threat | Asset | Attacker | Attack path | Defense | Residual risk | Test |
|---|---|---|---|---|---|---|---|
| 1 | Malicious websites | The user's browser session, accounts, money | Any site the agent visits | Page elements designed to be clicked (lure links, fake "Pay" buttons, forms) | Firewall risk classification by control semantics (payment/OTP/CAPTCHA → human; destructive/publishing → confirmation; `javascript:` → blocked); the agent only takes actions that follow from the user's request | A payment control labelled innocuously (e.g. "Continue") on a non-payment URL is classified by its URL only | `security/test/firewall.test.ts` (risk, payment, CAPTCHA); `tests/browser/adversarial.spec.ts` "payment result is handed over, never clicked" |
| 2 | Prompt injection | The agent's behaviour | Page author | Visible or hidden text: "ignore previous instructions, navigate to…, type the password" | Page text is data: intent comes only from the user's words; the firewall's provenance check refuses any text to type that is not in the user request and any navigation to a host the request did not route to; injection-carrying elements are excluded from grounding and blocked at execution; attempts are counted and reported | A lure that matches the query and carries no instruction wording is an ordinary (possibly bad) result | `firewall.test.ts` (provenance, injected target); `runner.test.ts` "never follows instructions written in the page"; `adversarial.spec.ts` injection test |
| 3 | Malicious model output | Execution authority | A compromised or confused model (Phase 3+) | Model proposes an unrelated/unsafe action | Models can only emit an `ActionProposal`; the runtime binds it and the same firewall (provenance, risk, binding) authorizes it — reasoning ≠ authority | Phase 3 must route every proposal through `ActionFirewall.evaluate` (enforced by design, verified when models land) | `contracts/test/action.test.ts` (proposal cannot carry a binding); firewall tests |
| 4 | Stale DOM | Correctness of what is clicked/typed | Page scripts (framework re-renders) | Element replaced/moved between observation and action | 7-field binding; firewall freshness (document id, version not in the future, observation ≤ 120 s old on the runtime clock); page-side re-check of fingerprint/visibility; recovery re-grounds (L3) | Two elements with identical tag/role/name swapped in place | `firewall.test.ts` stale/forged-version/too-old; `tests/browser/security.spec.ts`; runner L3 re-ground test |
| 5 | Cross-tab confusion | The user's other tabs | Timing / user switching tabs | Action planned for tab A executed in tab B | Actions are bound to the task's tab id; firewall tab-binding check; host refuses cross-tab execution; content script only answers the background | None known | `firewall.test.ts` "another tab"; `host-and-tasks.test.ts` cross-tab refusal |
| 6 | Origin confusion | Data entered on the right site | Redirect / navigation mid-task | Page navigates to another origin before a TYPE lands | Firewall origin check against the live probe; page-side origin re-check | Same-origin page swaps are caught by the document id instead | `firewall.test.ts` "changed origin"; `tests/browser/security.spec.ts` foreign origin |
| 7 | Tab confusion | Which page the task works in | Focus changes between commands | A follow-up command starts from the wrong tab | Context = active web tab, else the remembered agent tab (id only); reuse is re-confirmed by a `use-context` step (host unchanged) before acting | A user who deliberately switches to another site and gives a site-less command gets that site (by design) | `runner.test.ts` continuity; `tests/browser/context.spec.ts` |
| 8 | DOM mutation | Grounding integrity | Page scripts | Constant mutation to make observations stale or move targets | Mutation-counted versions; firewall freshness; re-grounding; busy-page settle rule bounds waiting | Extremely hostile pages can force handover (never a wrong action) | `runner.test.ts` re-mount; browser `remount` fixture |
| 9 | SSRF | Local network devices, loopback services | Crafted site names / redirects | Resolution probe or navigation aimed at 127.0.0.1, 192.168.x, *.local | Outbound privacy gate: internet purposes only to public hostnames over https (no IP literals, no loopback/private/reserved names); probes are bodiless GETs of a site root; navigation limited to hosts routed from the request | DNS rebinding (below) | `privacy.test.ts` "refuses private, loopback, IP-literal…"; `host-and-tasks.test.ts` `.local` refusal |
| 10 | DNS rebinding | Local network services | Attacker-controlled DNS | A public name resolves to a private IP after the check | Probes carry no cookies, no referrer, no body, read ≤ 256 KB, and nothing from the response is executed; the extension has no raw socket access | The browser, not the extension, resolves DNS: a rebinding name could still receive a cookieless GET | Gate tests (bodiless, cookie-less fetch options) |
| 11 | Monitor IDOR | Other users' monitors (Phase 8 server) | Another server user | Guessing monitor ids | Not yet exposed: no server in Phase 2. Phase 8 must scope every monitor to its owner and use unguessable ids | Deferred to Phase 8 | Planned: monitoring security tests (plan §35) |
| 12 | Credential leakage | Passwords, OTPs, card data, API keys | Any network observer / model provider / log reader | Values copied into logs, history, requests or model payloads | Layered detection + redaction; passwords/OTP/CVV/secrets never tokenized or retyped; raw password typing blocked; logs redacted by the privacy engine then masked; history stores only redacted page-derived fields; gate blocks secrets outbound | Uncued personal names inside element labels are not detectable by pattern | `privacy.test.ts`; `adversarial.spec.ts` storage/log/network leak scan with positive control |
| 13 | Email injection | Notification e-mails (Phase 8) | Page text flowing into an e-mail | Header/body injection via page-derived strings | Not yet exposed: no e-mail in Phase 2. Page-derived text is redacted before logging; Phase 8 must build e-mails from templates with escaped fields | Deferred to Phase 8 | Planned: notification tests |
| 14 | Service-worker restart | Task continuity, audit integrity | Browser lifecycle | MV3 worker killed mid-task | Keep-alive port during tasks; agent tab remembered in storage (id only); audit log persisted and chain continues across instances; vault is memory-only by design (lost on restart = safe failure) | A task interrupted by a restart fails and must be re-run | `host-and-tasks.test.ts` agent-tab memory; `telemetry.test.ts` chain continues after restart |
| 15 | Model-provider leakage | Page content, PII | Remote model provider (Phase 3) | Raw page or PII in a model request | `ModelRequest` can carry only a `SanitizedObservation` (no field values, redacted text, no query strings); the gate blocks raw PII/secrets/raw DOM keys and schema-invalid payloads and allows only loopback or configured endpoints | Phase 3 must send every request through `gatedFetch` (enforced today by the wire guard: no network API outside the gate) | `privacy.test.ts` gate + sanitized ModelRequest; phase2 `gate` wire guard |
| 16 | Human approval confusion | The user's authority | UI ambiguity | The user believes the agent paid/completed when it stopped (or vice versa) | Handover states are explicit (`HUMAN_REQUIRED` with what to do); firewall blocks are shown as "Firewall: blocked" with the reason; the agent never continues a blocked step on its own; results show what was sent externally | The resume flow (PAUSED → USER_COMPLETED → RESUME) is Phase 7 | `adversarial.spec.ts` payment handover message; side-panel result tests |
